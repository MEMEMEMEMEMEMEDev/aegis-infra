# mirror-images — THIRD-PARTY images that the platform mirrors into the
# internal registry and signs with the aegis key.
#
# WHY THIS FILE EXISTS
# The require-aegis-signature ClusterPolicy demands our own signature for
# every Pod in a tenant namespace (imageReferences '*'). A public image
# CANNOT run there: it is not signed with our key, and we are not going
# to weaken the policy for convenience. The correct way out is to pull
# it, SCAN it and sign it ourselves — which is exactly what the
# mirror-images job does. The result is that everything running in a
# tenant went through the same control, ours or third-party alike.
#
# FORMAT
#   <source>@<digest>   <destination>:<tag>
#
# The source is pinned BY DIGEST, not by tag. A tag is a mutable
# pointer: whoever controls the source registry can repoint it at other
# content without us noticing. The digest is the content. The tag stays
# in the comment so a human knows what they are reading.
#
# HOW TO UPDATE AN IMAGE
#   1. crane digest <source>:<new-tag>
#   2. edit the line here (digest AND destination tag)
#   3. commit + push  →  run the mirror-images job
#   4. bump the reference in the manifest that consumes it
# Step 4 is separate on purpose: mirroring does not deploy. Pulling a
# new image and putting it in production are two distinct decisions.
#
# Empty lines and lines starting with # are ignored.

# --- storage --------------------------------------------------------
# Garage v2.3.0 — self-hosted S3 (Deuxfleurs, a French cooperative with
# NGI funding; releases every 3-4 months and two parallel branches).
#
# Chosen over MinIO, which has NOT published a release since 2025-09-07:
# a storage server left unpatched for 10 months is not an option for
# third-party data. Also over SeaweedFS, the most active of the three,
# but built as master+volume+filer+gateway: far more machinery than a
# handful of apps need.
#
# THIS IMAGE'S FILESYSTEM IS TWO ENTRIES: the root directory and a 71 MB
# static binary. No shell, no package manager, no libc, no utilities. If
# somebody finds an RCE there is nothing to chain it to: no sh, no curl,
# no apk. And because the binary is r-xr-xr-x, it runs under any UID =>
# runAsNonRoot even though the image declares root.
#
# KNOWN LIMITATIONS, which shape how it is used:
#   - NO object versioning and no object lock. Whatever is deleted or
#     overwritten is gone. An immutable backup CANNOT rest on this.
#   - NO server-side encryption. Objects sit in plain text on the disk,
#     which is not encrypted either (pending item #1 of the instance).
#     For customer data that has to be solved first.
#   - Permissions per key-and-bucket instead of IAM. Less power, and
#     less to get wrong with.
docker.io/dxflrs/garage@sha256:866bd13ed2038ba7e7190e840482bc27234c4afaf77be8cfa439ae088c1e4690	garage:v2.3.0

# --- CI toolchains --------------------------------------------------
# golang:1.26.6-alpine — compiles the ai-gateway in the pipeline.
#
# WHY HERE AND NOT AN aegis-ci-go IN ci-images/. The aegis-ci-* images
# exist when something has to be ADDED to the official one: aegis-ci-node
# carries git because the portfolio consumes a dependency from a private
# repo; the cosign and crane ones exist because the official images are
# distroless and Jenkins' `container(){ sh }` needs a shell. For Go
# nothing has to be added: the gateway module does not have a single
# external dependency (`GOPROXY=off` in the pipeline enforces it), so it
# needs neither network nor git. A derived image that adds nothing would
# be one more link in the supply chain for zero benefit.
#
# DECLARED COUPLING: the destination tag MUST match the `image` of the
# `go` container in ai-gateway/Jenkinsfile. It is inter-repo and not
# derivable at runtime; if the two diverge, the symptom is
# ImagePullBackOff — visible, not silent.
#
# The version follows the toolchain on the operator's machine, so that
# "it builds on my machine" and "it builds in CI" cannot mean two
# different things.
#
# 1.26.5 -> 1.26.6 on 2026-08-17, and not out of taste: build 12 of the
# gateway BLOCKED at the scan with 8 HIGH from the 1.26.5 stdlib
# (CVE-2026-33818 and company: asn1, net/http HTTP/2, html/template,
# encoding/xml, net/url, crypto/tls — all fixed in 1.26.6). Trivy reads
# the buildinfo of the ELF, so the patch belongs to the COMPILER: no
# line of gateway code can fix this.
public.ecr.aws/docker/library/golang@sha256:3889b425f035be855a72fb4755265311293b6d414521f0a519d819df32222d83	golang:1.26.6-alpine

# --- application runtimes -------------------------------------------
# python:3.12-slim — base of the engine-cpu (#26), build AND runtime.
#
# WHY 3.12 AND NOT THE LATEST: onnxruntime and ctranslate2 publish
# wheels up to 3.13; with anything newer, pip builds from source or
# fails with an error that looks nothing like "that version is too new".
# It is the SAME pin as the requires-python of the module's pyproject —
# if they diverge, the Containerfile build fails hard inside kaniko.
#
# WHY slim AND NOT distroless, which is the criterion for the BFF: here
# the Containerfile has a RUN (pip install of native wheels) and the
# runtime needs the libstdc++/libgomp those wheels link against. A
# distroless would force a multi-stage copying site-packages and its
# .so files by hand — more surface to get wrong than it removes. What
# the pod does not need is stripped by the Deployment: no root, no
# escalation, read-only root filesystem.
#
# The source digest is the SAME on public.ecr.aws as on Docker Hub;
# measured with both APIs on 2026-08-17 before choosing, as was done
# with nginx-unprivileged.
public.ecr.aws/docker/library/python@sha256:2c941e860699f878900b0edc2403613c234d4b32eda3cc9fa7036991a2a63c4a	python:3.12-slim
# nodejs22 distroless — runtime of the portfolio BFF.
#
# WHY DISTROLESS AND NOT node:22-alpine. The official one was tried on
# 2026-08-02 and Trivy BLOCKED it, rightly so: node:22.23.1-alpine ships
# npm installed, and the dependencies bundled WITH NPM carried a CRITICAL
# (CVE-2026-59873, gzip bomb in node-tar) plus several HIGH (sigstore,
# picomatch, brace-expansion). None of those ever execute in production:
# the BFF runs `node src/server.js` and its dependencies are installed
# in CI with `npm ci`, not in the pod.
#
# In other words: the scan blocked because of a package manager the
# runtime does not use. The way out is NOT a Trivy exception — it is
# removing the package manager. Same criterion as with /usr/bin/pebble
# in the engine image: excise rather than except. And the same criterion
# that picked garage, praised in this very file precisely for having
# neither shell nor package manager.
#
# This image is node and nothing else: no npm, no shell, no apt, no
# coreutils. ENTRYPOINT is already /nodejs/bin/node and the user is
# 65532, so the BFF Containerfile only sets WORKDIR, COPY and the CMD
# with the path to the script.
#
# WHY debian13 AND NOT debian12. The first attempt with distroless was
# on debian12 and Trivy blocked it TOO — but this time rightly, and over
# something node DOES use: libssl3 3.0.18 with a CRITICAL
# (CVE-2026-31789, heap overflow in OpenSSL) and five HIGH, all with a
# fix available in 3.0.19. Debian had the fix; distroless had not yet
# rebuilt that base.
#
# The difference between the two blocks matters and is worth not
# confusing: the node-alpine one was noise (CVEs in a package manager
# the runtime never executes) and was solved by removing the manager;
# the debian12 one was a real vulnerability in the TLS library of the
# process, and was solved by moving to a patched base. Same verdict from
# the scanner, two different causes.
#
# debian13 (trixie) scanned with ZERO findings. That was verified BEFORE
# running this job again, with a single-use trivy Job against the same
# server: two failed runs in a row over a slow link are expensive.
#
# BEWARE THE EASY CONFUSION: aegis-ci-node (ci-images/) does NOT serve
# this purpose and this one does NOT serve that. The CI image needs npm
# and git in order to build, and the ci-images job neither scans nor
# signs; org-portafolio sits in Kyverno's enforce zone and demands a
# signature. Two different images for two different jobs: one builds,
# the other runs.
gcr.io/distroless/nodejs22-debian13@sha256:a2723a2817c5b01b8e7b98d567bc8b5a6b0e713e25bfb0a82b6ade4b9db06f50	nodejs-distroless:22

# nginx-unprivileged 1.31.3-alpine — base of the THREE static fronts:
# portafolio, blog and ejemplo.
#
# WHY THE unprivileged VARIANT AND NOT PLAIN nginx. Two reasons, and
# both are mandatory on this platform:
#
#   1. It listens on 8080. A tenant's NetworkPolicy only allows ingress
#      from the edge to 8080; with regular nginx (port 80) the pod
#      starts up fine and NEVER receives traffic. That is the worst
#      class of failure: the silent one.
#   2. It runs as UID 101, not root. Tenant namespaces sit under the
#      `restricted` Pod Security Standards: a container that asks for
#      root is REJECTED at admission and the pod never comes to exist.
#
# WHY IT IS ONLY BEING MIRRORED NOW, which is the part really worth
# telling.
#
# It was not here. The three fronts pulled it from Docker Hub ON EVERY
# BUILD. It surfaced on 2026-08-09, when build 38 of the portfolio died
# like this:
#
#   Retrieving image nginxinc/nginx-unprivileged from index.docker.io
#   error building image: Get "https://index.docker.io/v2/": ...
#
# And the failed build is the lesser consequence. The greater one is
# that we were signing the RESULTING artifact with cosign while nobody
# had verified the base it was built on — and by TAG, no less. The
# signature policy was doing exactly what it promises —verifying what we
# sign— and even so there was unverified ground underneath. That is
# precisely the hole this file exists to close.
#
# The source digest is the SAME on public.ecr.aws as on Docker Hub; it
# was measured with `crane digest` against both before choosing. So
# using ECR costs nothing and dodges the Hub's rate limits.
public.ecr.aws/nginx/nginx-unprivileged@sha256:334d92979f15aaecd5dd50af5105e1230e2bb70765d45b1e2f964e7c5eda81c3	nginx-unprivileged:1.31.3-alpine
